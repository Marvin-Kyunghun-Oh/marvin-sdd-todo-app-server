# Marvin's Todo App 서버

할 일 앱의 API 서버입니다. 앱 자체보다 **명세 주도 개발(SDD)과 테스트 주도 개발(TDD)로 끝까지 만들어 본 과정**이 이 저장소의 주제입니다. 기능은 일부러 작게 잡았고, 대신 "문서 → 테스트 → 코드"의 순서를 어기지 않는 데 집중했습니다.

## 어떻게 만들었나

단계마다 산출물을 만들고 사람이 승인한 뒤에 다음 단계로 넘어갔습니다. 단계가 올라갈수록 아래 문서가 위 문서를 따릅니다. 충돌하면 위 문서가 기준입니다.

| 단계 | 산출물 | 위치 | 우선순위 |
| --- | --- | --- | --- |
| 0. 헌법 | 개발 원칙, 제약 조건, 작업 방식 | [`CLAUDE.md`](CLAUDE.md) | 1 |
| 1. 명세 | PRD, 요구사항과 수용 기준(AC), 결정 기록 | [`docs/spec/`](docs/spec) | 2 |
| 2. 기술 계획 | TRD, 데이터 모델, API 명세, 결정 기록 | [`docs/plan/`](docs/plan) | 3 |
| 3. 작업 목록 | 24개 작업과 AC → 작업 추적표 | [`docs/tasks/TASKS.md`](docs/tasks/TASKS.md) | 4 |
| 4. 구현 | 코드와 테스트 | [`src/`](src) | 5 |

### SDD: 명세가 기준이다

- 수용 기준(AC) 56개를 먼저 확정했고, 테스트는 모두 AC에서 도출했습니다.
- 테스트의 `@DisplayName`은 `AC 번호 + 명세의 Given·When·Then`을 그대로 씁니다. 명세의 문장을 검색하면 그에 해당하는 테스트가 나옵니다.
- 명세에 없는 기능은 만들지 않습니다. 필요해 보이면 구현하지 않고 명세 변경을 제안합니다.
- **역류 규칙:** 구현 중 명세나 설계의 빈틈을 발견하면 코드보다 문서를 먼저 고치고, 사람의 승인을 받은 뒤 구현을 이어갑니다. 이 과정이 실제로 여러 번 있었고 모두 문서 이력에 남아 있습니다.
  - 읽을 수 없는 요청과 알 수 없는 `status` 값의 처리(D-30, D-31)
  - 숫자가 아닌 id, `completed` 누락, 없는 주소, 서버 오류 등 열 가지 실패 상황(D-32~D-39)
  - 구현 중 발견한 작업 목록의 빈틈(생성자 불변식 테스트 추가, 구성 조립 케이스를 T21에서 T13으로 이동)
- 사람이 판단할 지점은 각 문서 맨 앞의 "한눈에 보기 (사람용 요약)"에 평문으로 모아 두었고, 에이전트용 상세와 나눠 씁니다.

### TDD: 실패하는 테스트가 먼저다

- 작업 하나당 Red → Green → Refactor를 지키고, **커밋도 작업 하나당 하나**입니다. 테스트와 그것을 통과시키는 코드는 같은 커밋에 들어 있습니다.
- Red에서는 테스트가 "기능 부재" 때문에 실패하는지 확인합니다. 먼저 통과해 버리는 테스트는 의미를 의심하고 보고합니다(통합 테스트는 설정을 일부러 망가뜨려 실제로 실패하는지 확인했습니다).
- Green은 통과에 필요한 최소 코드만 씁니다. 예를 들어 기한 지남 값은 T08까지 `false` 고정으로 두었다가, T09의 테스트가 실제 계산을 끌어냈습니다.
- 동시성도 테스트 먼저입니다. 일부러 스레드에 안전하지 않은 구현으로 테스트를 실패시킨 뒤 `AtomicLong`과 `computeIfPresent`로 고쳤습니다.
- 테스트는 층마다 책임이 다릅니다. 규칙이 사는 층에서 본격적으로 검증하고, 다른 층은 연결과 응답 모양만 봅니다.

| 층 | 도구 | 확인하는 것 |
| --- | --- | --- |
| 도메인 | JUnit만 (Spring 없음) | 입력 규칙, 기한 지남 판정 |
| 서비스 | JUnit + Mockito, `Clock.fixed` | 흐름, 요약 계산, 실패 시 저장소 미호출 |
| 저장소 | JUnit | 등록 순서, 번호 발급, 원자적 수정, 동시성 |
| 웹 슬라이스 | `@WebMvcTest` + `@MockitoBean` | 상태 코드, 오류 코드와 확정 문구, 요청 읽기 정책 |
| 통합 | `@SpringBootTest` + `MockMvc` | 실제 설정, 대표 시나리오, 실패 시 상태 불변 |

### 구조

```
presentation ──▶ application ──▶ domain ◀── persistence
config (모든 층을 조립하는 구성 루트)
```

- 의존은 바깥에서 안쪽으로만 향합니다. `domain`은 Spring을 모릅니다.
- 시간은 `Clock`으로 주입하고, 테스트에서는 고정된 시계로 바꿉니다. "오늘"은 한국 시간(`Asia/Seoul`) 기준입니다.
- 저장소는 인메모리이고, 서버를 끄면 데이터는 사라집니다.

## 실행하기

Java 21이 필요합니다.

```bash
./gradlew build       # 테스트와 커버리지 검증까지 포함
./gradlew test        # 테스트만

# 샘플 데이터가 채워진 상태로 실행 (기한 지남, 오늘 마감, 미래, 마감 없음, 완료)
./gradlew bootRun --args='--spring.profiles.active=local'
```

호출 계약(엔드포인트 6개, 오류 코드와 확정 문구)은 [`docs/plan/API_SPEC.md`](docs/plan/API_SPEC.md)에 있습니다.

## 기술 스택

Java 21, Spring Boot 4.1.2, Gradle 9.8.2(Kotlin DSL), JUnit 6, Mockito, JaCoCo. 새 의존성은 사람의 승인을 받은 뒤에만 추가했고, 입력 검증 라이브러리는 쓰지 않고 직접 구현했습니다.

## 알려진 한계

- CORS를 지원하지 않습니다. 화면과 서버를 다른 주소에 띄우면 브라우저가 막을 수 있습니다.
- 가족 이모지나 국기는 글자 수를 2자 이상으로 셉니다. 줄바꿈 없는 공백(U+00A0)과 폭 없는 공백(U+200B)은 공백으로 보지 않습니다.
- 로그인, 알림, 검색, 정렬 변경, 페이지 나눔은 범위 밖입니다.
