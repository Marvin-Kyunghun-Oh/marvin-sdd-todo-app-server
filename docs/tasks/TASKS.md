# TASKS — Marvin's Todo App 서버

> SDD 3단계(Tasks) 산출물. 상태: **확정 (2026-11-11, Marvin-Oh)**

## 한눈에 보기 (사람용 요약)
> 승인은 이 부분만 읽고 한다. 아래 상세가 이 요약과 맞는지는 리뷰가 확인한다.

- 작업은 모두 24개이고, 하나가 커밋 하나다. 각 작업은 테스트를 먼저 쓰고 그 테스트를 통과시키는 코드를 같은 커밋에 넣는다.
- 첫 작업에서 프로젝트 틀과 앱 시작 지점을 함께 만들고 "앱이 뜬다"는 테스트까지 붙인다. 시작 지점이 없으면 빌드가 처음부터 실패하기 때문이다. 코드가 시작 지점뿐인 첫 시점에도 테스트가 코드의 80% 이상을 지나가도록, 테스트에서 시작 지점을 직접 한 번 실행한다. 이때 남는 앱이 다른 테스트에 영향을 주지 않는지 첫 작업에서 같이 확인한다.
- 순서는 안쪽부터다. 프로젝트 틀, 제목·설명·마감일·기한 지남 규칙, 저장, 일을 처리하는 부분, 요청을 받는 부분, 전체 연결, 샘플 데이터, 마무리 순이다. 바깥 층은 이미 끝난 안쪽 층 위에만 쌓인다.
- 요청을 받는 부분에서는 "이상한 요청을 읽을 수 없다고 돌려보내는 공통 규칙"을 오류 응답 틀 바로 뒤에 둔다. 뒤의 작업들이 이 규칙을 미리 켜 두지 않아도 되고, 이 규칙의 테스트도 처음에 실패하는 것을 확인할 수 있다.
- 명세의 수용 기준 56개는 모두 최소 한 작업의 테스트와 이어진다. 상세 장 마지막의 표에서 확인할 수 있다.
- 테스트 이름은 명세에 쓴 문장을 그대로 쓰고 앞에 기준 번호를 붙인다. 층마다 다른 확인 내용(저장소 호출, 상태 코드 등)은 이름이 아니라 케이스 설명에만 적는다. 값이 여러 개인 경우는 테스트 하나에 값을 돌려 가며 확인한다.
- 같은 기준을 여러 층에서 확인하는 경우, 규칙이 사는 층에서 본격적으로 확인하고 다른 층에서는 연결과 응답 모양만 확인한다.
- 사람이 알아 둘 결정 두 가지가 있다.
  - 서버 내부 오류 응답은 실제 서버로는 일부러 일으킬 수 없다. 그래서 테스트 폴더에만 두는 "일부러 오류를 내는 테스트용 주소"를 쓴다. 제품에는 포함되지 않고 명세에 없는 주소도 늘지 않는다.
  - 명세의 수용 기준에 직접 대응하지 않는 작업이 세 개 있다. 프로젝트 틀 만들기, 로컬 샘플 데이터, 마무리이고, 모두 설계 문서에 근거가 있다.
- 한 작업이 끝날 때마다 한 일과 테스트 결과를 보고하고, 확인을 받은 뒤에 다음으로 넘어간다.
- 가장 큰 작업(통합 시나리오)은 진행 중 커밋 하나에 담기 어려우면 멈추고 나눌지 묻는다. 목록 처리는 "목록·보기·요약"과 "기한 지남 판정" 두 작업으로 나눠 두었다.

## 0. 공통 규칙
- **한 작업 = 한 커밋.** 테스트와 그 테스트를 통과시키는 코드는 같은 커밋에 넣는다. 커밋 메시지는 `<타입>: <요약>` (CLAUDE.md 2.6.2~2.6.3). 작업 하나가 끝나면 보고하고 확인을 받는다 (2.6.4).
- **TDD 순서.** 작업 안의 테스트 케이스는 한 번에 하나씩 Red → Green → Refactor로 진행한다 (CLAUDE.md 2.1). 아래 케이스 순서가 그대로 진행 순서다. 먼저 실패하지 않는 케이스를 발견하면 멈추고 보고한다.
- **테스트 이름 규칙.**
  - `@DisplayName`은 `AC 번호 + 명세의 Given·When·Then을 한 문장으로 이은 것`이다. 예: `AC-11-1 할 일이 있을 때 삭제하면 그 할 일은 이후 목록과 요약에서 사라진다`.
  - 층마다 다른 확인 내용(저장소 호출 여부, 상태 코드, 응답 모양)은 이름에 넣지 않고 아래 케이스의 **확인:** 설명에만 적는다.
  - 같은 AC 이름이 여러 층에 나올 수 있다. 테스트 클래스 이름(`*ServiceTest`, `*ControllerTest` 등)이 층을 구분한다.
  - 입력값이 여러 개인 AC는 `@ParameterizedTest` 하나로 쓴다. 이름은 하나이고 입력값은 케이스 설명에 적는다 (이미 들어 있는 JUnit 기능이라 새 의존성이 아니다).
  - AC가 없는 케이스(저장소 계약, 불변식, 샘플 데이터 등)는 근거 문서의 문장을 이름으로 쓴다.
  - 확정 안내 문구는 웹 슬라이스 이후의 테스트가 정확한 문장으로 검사한다 (D-24). 도메인·서비스 층은 오류 종류(코드)로 확인한다.
- **층별 책임.** 규칙이 사는 층에서 본격적으로 검증한다. 도메인은 규칙, 서비스는 흐름과 "실패하면 저장소를 건드리지 않음", 웹은 상태 코드·오류 코드·확정 문구·요청 읽기, 통합은 실제 연결과 대표 시나리오.
- **테스트 종류 표기.** 단위(도메인) / 단위(서비스) / 단위(저장소) / 웹 슬라이스 / 통합 / 빌드.
- **500 확인 방식.** 웹 슬라이스에서는 `@MockitoBean TodoService`가 예상 못한 예외를 던지게 한다 (T20). 통합에서는 `src/test`에만 있는 예외 던지는 컨트롤러를 `@TestConfiguration`으로 켜서 실제 500을 확인한다 (T21). 제품 코드에는 아무것도 추가하지 않는다.
- **`TodoApplication`** (부트 진입점)은 T01에서 만든다. 진입점이 없으면 `bootJar`가 실패해 `./gradlew build`가 처음부터 실패하기 때문이다.
- **AC가 없는 작업:** T01(골격, TRD 1장·9장), T23(샘플 데이터, TD-13, TRD 7장), T24(마무리).
- **전역 JSON 설정**(강제 변환 끄기, 알 수 없는 필드 거부)은 T14에서 처음 켜고, 그 전에는 켜지 않는다. 이후 작업은 같은 효과를 내는 중복 케이스를 쓰지 않는다 (먼저 실패하지 않는 테스트를 만들지 않기 위해). 실제 서버 설정에서의 확인은 T21이 맡는다.

### T01. Gradle 프로젝트 골격, 앱 진입점, JaCoCo 검증 연결
- **커밋:** `chore: Gradle 프로젝트 골격과 앱 진입점, JaCoCo 검증 추가`
- **AC:** 없음 (근거: TRD 1장, 9장, TD-16, TD-17, TD-23, TD-29, TD-31, CLAUDE.md 4장)
- **종류:** 통합(앱이 뜬다) + 빌드
- **선행:** 없음
- **내용:** Gradle 9.8.2 wrapper(Kotlin DSL), Spring Boot 4.1.2, `spring-boot-starter-webmvc`, `spring-boot-starter-webmvc-test`, 자바 21 툴체인, `jacoco` 플러그인(라인 80%, `check`에 연결), `com.marvin.todo.TodoApplication`. 새 의존성은 이 둘뿐이다.
- **진행 순서:** (1) 프로젝트 파일만 있고 진입점이 없는 상태에서 `./gradlew build`가 실패하는 것을 먼저 확인해 보고한다. (2) 아래 케이스 1을 쓰고 컴파일 실패(진입점 없음)를 Red로 확인한다. (3) 진입점을 만들어 Green으로 만든다. (4) `build`를 실행해 JaCoCo 검증이 실패하면 케이스 2를 Red로 삼는다.
- **테스트 케이스:**
  1. **애플리케이션이 뜬다** — 확인: `@SpringBootTest`로 모킹 없이 컨텍스트가 뜬다.
  2. **애플리케이션 시작 지점을 실행하면 정상적으로 시작된다** — 확인: `TodoApplication.main`을 `--spring.main.web-application-type=none`으로 한 번 호출해 예외 없이 끝난다. 목적은 시작 지점의 줄을 커버리지에 포함하는 것이다 (진입점 제외 같은 예외를 두지 않기 위함).
- **함께 확인할 것 (보고에 포함):**
  - `main` 호출로 뜬 앱이 남아 있어도 다른 테스트에 영향이 없는지: 전체 테스트를 두 번 연속 실행하고, 포트나 상태 충돌이 없는지 본다. 문제가 있으면 멈추고 보고한다.
  - `./gradlew build`가 성공하고 `check --dry-run`에 `jacocoTestCoverageVerification`이 포함되며, 측정된 라인 커버리지 값.

### T02. 제목 검증
- **커밋:** `feat: 제목 검증 추가`
- **AC:** AC-01-3, AC-02-1, AC-02-2, AC-02-3, AC-02-4 (+ 입력 규칙의 글자 수 정의, DATA_MODEL 2.1~2.2)
- **종류:** 단위(도메인)
- **선행:** T01
- **테스트 케이스** (`NewTodo.of`, 도메인 예외는 오류 코드를 가진다):
  1. **AC-02-1 제목이 비어 있을 때 추가하면 할 일은 만들어지지 않고 "제목을 입력해 주세요."라는 안내가 돌아온다** — 확인: 제목 없음 오류(`TITLE_REQUIRED`). 입력 `null`, `""` (파라미터화).
  2. **AC-02-2 제목이 공백 문자로만 이루어져 있을 때 추가하면 비어 있는 경우와 똑같이 거부된다** — 확인: 제목 없음 오류. 입력 스페이스, 탭, 줄바꿈, 전각 공백 (파라미터화).
  3. **AC-01-3 제목 앞뒤에 공백이 있을 때 추가하면 공백이 제거된 제목으로 저장된다** — 확인: 만들어진 값의 제목이 제거된 값이고 가운데 공백은 그대로다.
  4. **AC-02-4 제목이 정확히 100자일 때 추가하면 정상적으로 만들어진다** — 확인: 오류 없이 만들어진다.
  5. **AC-02-3 제목이 101자일 때 추가하면 할 일은 만들어지지 않고 "제목은 100자 이하로 입력해 주세요."라는 안내가 돌아온다** — 확인: 제목 너무 김 오류(`TITLE_TOO_LONG`).
  6. **글자 수는 한글, 영문, 숫자, 공백, 이모지 모두 1자로 센다 (입력 규칙)** — 확인: 이모지로 100자인 제목은 만들어지고 101자는 거부된다.
  7. **앞뒤 공백을 제거한 뒤에 글자 수를 센다 (입력 규칙)** — 확인: 공백 포함 102자지만 제거 후 100자인 제목은 만들어진다.

### T03. 설명 검증과 정규화 (수정 입력의 제목·설명)
- **커밋:** `feat: 수정 입력의 제목·설명 검증 추가`
- **AC:** AC-02-5, AC-02-6 (+ 입력 규칙의 설명 정규화 D-27, DATA_MODEL 2.1, 2.4, 4.2)
- **종류:** 단위(도메인)
- **선행:** T02
- **테스트 케이스** (`TodoUpdate.of`, 마감일은 T04에서 추가하므로 이 작업에서는 없음으로 전달):
  1. **AC-02-5 기존 할 일이 있을 때 제목을 비우거나 공백만 넣어 수정하면 수정은 거부되고 "제목을 입력해 주세요."라는 안내가 돌아오며 기존 내용은 그대로다** — 확인: 제목 없음 오류가 나고 값 객체가 만들어지지 않는다. 입력 `""`, 공백뿐 (파라미터화).
  2. **AC-02-6 설명이 1,001자일 때 추가 또는 수정하면 거부되고 "설명은 1,000자 이하로 입력해 주세요."라는 안내가 돌아온다** — 확인: 설명 너무 김 오류(`DESCRIPTION_TOO_LONG`).
  3. **설명이 정확히 1,000자이면 만들어진다 (입력 규칙)** — 확인: 오류 없이 만들어진다.
