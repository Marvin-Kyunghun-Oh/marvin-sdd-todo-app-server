# TASKS — Marvin's Todo App 서버

> SDD 3단계(Tasks) 산출물. 상태: **초안 (2026-11-11)**

## 한눈에 보기 (사람용 요약)
> 승인은 이 부분만 읽고 한다. 아래 상세가 이 요약과 맞는지는 리뷰가 확인한다.

- 작업은 모두 23개이고, 하나가 커밋 하나다. 각 작업은 테스트를 먼저 쓰고 그 테스트를 통과시키는 코드를 같은 커밋에 넣는다.
- 순서는 안쪽부터다. 프로젝트 틀을 만들고, 제목·설명·마감일·기한 지남 규칙, 저장, 일을 처리하는 부분, 요청을 받는 부분, 전체 연결, 샘플 데이터, 마무리 순으로 간다. 바깥 층은 이미 끝난 안쪽 층 위에만 쌓인다.
- 명세의 수용 기준 56개는 모두 최소 한 작업의 테스트와 이어진다. 상세 장 마지막의 표에서 확인할 수 있다.
- 테스트 이름은 명세에 쓴 문장을 그대로 쓰고, 찾기 쉽도록 앞에 기준 번호를 붙인다.
- 같은 기준을 여러 층에서 확인하는 경우, 규칙이 사는 층에서 본격적으로 확인하고 다른 층에서는 연결과 응답 모양만 확인한다.
- 사람이 알아 둘 결정 두 가지가 있다.
  - 서버 내부 오류 응답은 실제 서버로는 일부러 일으킬 수 없다. 그래서 테스트 폴더에만 두는 "일부러 오류를 내는 테스트용 주소"를 쓴다. 제품에는 포함되지 않고 명세에 없는 주소도 늘지 않는다.
  - 명세의 수용 기준에 직접 대응하지 않는 작업이 두 개 있다. 프로젝트 틀 만들기와 로컬 샘플 데이터이고, 둘 다 설계 문서에 근거가 있다.
- 한 작업이 끝날 때마다 한 일과 테스트 결과를 보고하고, 확인을 받은 뒤에 다음으로 넘어간다.
- 가장 큰 작업(요청 읽기 규칙, 통합 시나리오)은 진행 중 커밋 하나에 담기 어려우면 멈추고 나눌지 묻는다.

## 0. 공통 규칙
- **한 작업 = 한 커밋.** 테스트와 그 테스트를 통과시키는 코드는 같은 커밋에 넣는다. 커밋 메시지는 `<타입>: <요약>` (CLAUDE.md 2.6.2~2.6.3). 작업 하나가 끝나면 보고하고 확인을 받는다 (2.6.4).
- **TDD 순서.** 작업 안의 테스트 케이스는 한 번에 하나씩 Red → Green → Refactor로 진행한다 (CLAUDE.md 2.1). 아래 케이스 순서가 그대로 진행 순서다.
- **테스트 이름.** `@DisplayName`에 `AC-xx-x` 번호와 REQUIREMENTS의 문장을 쓴다. 예: `AC-02-1 제목이 비어 있을 때 추가하면 할 일은 만들어지지 않는다`. 확정 문구가 있는 경우 웹 슬라이스 이후의 테스트가 정확한 문장을 검사한다 (D-24). AC가 없는 케이스는 근거 문서의 문장을 쓴다.
- **층별 책임 (Q6).** 규칙이 사는 층에서 본격적으로 검증한다. 도메인은 규칙, 서비스는 흐름과 "실패하면 저장소를 건드리지 않음", 웹은 상태 코드·오류 코드·확정 문구·요청 읽기, 통합은 실제 연결과 대표 시나리오.
- **테스트 종류 표기.** 단위(도메인) / 단위(서비스) / 단위(저장소) / 웹 슬라이스 / 통합 / 빌드.
- **500 확인 방식 (Q3).** 웹 슬라이스에서는 `@MockitoBean TodoService`가 예상 못한 예외를 던지게 한다 (T19). 통합에서는 `src/test`에만 있는 예외 던지는 컨트롤러를 `@TestConfiguration`으로 켜서 실제 500을 확인한다 (T20). 제품 코드에는 아무것도 추가하지 않는다.
- **`TodoApplication`** (부트 진입점)은 `@WebMvcTest`가 처음 필요한 T12에서 만든다.
- **AC가 없는 작업:** T01(골격, TRD 1장), T22(샘플 데이터, TD-13, TRD 7장), T23(마무리).

### T02. 제목 검증
- **커밋:** `feat: 제목 검증 추가`
- **AC:** AC-01-3, AC-02-1, AC-02-2, AC-02-3, AC-02-4 (+ 입력 규칙의 글자 수 정의, DATA_MODEL 2.1~2.2)
- **종류:** 단위(도메인)
- **선행:** T01
- **테스트 케이스** (`NewTodo.of`, 도메인 예외는 오류 코드를 가진다):
  1. AC-02-1 제목이 비어 있을 때 추가하면 할 일은 만들어지지 않는다 (제목 없음 오류). `null`과 `""` 모두.
  2. AC-02-2 제목이 공백 문자로만 이루어져 있으면 비어 있는 경우와 똑같이 거부된다. 스페이스, 탭, 줄바꿈, 전각 공백.
  3. AC-01-3 제목 앞뒤에 공백이 있을 때 추가하면 공백이 제거된 제목으로 저장된다. 가운데 공백은 그대로 둔다.
  4. AC-02-4 제목이 정확히 100자이면 정상적으로 만들어진다.
  5. AC-02-3 제목이 101자이면 할 일은 만들어지지 않는다 (제목 너무 김 오류).
  6. 글자 수는 한글, 영문, 숫자, 공백, 이모지 모두 1자로 센다. 이모지로 100자인 제목은 만들어지고 101자는 거부된다.
  7. 앞뒤 공백을 제거한 뒤에 글자 수를 센다. 공백 포함 102자지만 제거 후 100자인 제목은 만들어진다.

### T06. 저장소 인터페이스와 인메모리 구현

- **종류:** 단위(저장소)
- **선행:** T02, T05
- **테스트 케이스** (테스트마다 새 저장소):

  2. 만들 때마다 번호가 1부터 하나씩 늘어난다.
  3. AC-03-1 "가", "나", "다"가 이 순서로 등록되어 있으면 목록은 "가", "나", "다" 순서로 돌아온다.

  8. 수정은 대상을 새 값으로 교체하고 새 값을 돌려준다. 수정이 돌려준 할 일의 번호가 다르면 거부한다.
  9. AC-11-2 삭제하면 true이고 이후 같은 번호는 찾을 수 없으며, 없는 번호를 삭제하면 false이다.
  10. AC-12-1 삭제된 번호는 다시 발급되지 않는다.
  11. 여러 스레드가 동시에 만들어도 번호가 겹치지 않는다.
  12. 여러 스레드가 같은 할 일을 동시에 수정해도 변경이 유실되지 않는다 (원자적 수정).
